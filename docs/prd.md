# 企业OA管理系统 - 产品需求文档 (PRD)

- 版本：v1.0
- 状态：草稿
- 最后更新：2026-07-23

---

## 1. 项目背景与目标

### 1.1 背景
企业内部的请假、报销等审批流程目前分散在纸质单据或微信/钉钉群聊中处理，存在以下问题：
- 审批效率低，容易遗漏或延误
- 无留痕记录，出现纠纷时无法追溯
- HR/管理员无法统一查看全公司的人员架构和审批状态
- 数据分散，无法做统计分析（比如某部门本月请假率）

### 1.2 目标
搭建一个轻量级企业内部管理系统（OA），实现：
- 统一的用户账号与权限管理
- 清晰的组织架构（部门、汇报关系）管理
- 线上化的审批流程（请假、报销），有留痕、可追溯
- 审批状态实时通知
- 基础的数据看板，供管理层查看统计信息

### 1.3 非目标（明确本期不做什么，避免范围蔓延）
- 不做移动端App，仅支持Web端
- 不做工资/薪酬计算模块
- 不做考勤打卡功能（本期只做请假/报销审批）
- 不做多语言/国际化支持

## 2. 用户角色定义

| 角色 | 说明 | 核心权限 |
|---|---|---|
| 普通员工 (Employee) | 公司大多数员工 | 提交审批申请、查看自己的申请记录、查看自己的待办通知 |
| 部门主管 (Manager) | 部门负责人 | 员工权限 + 审批本部门员工的申请、查看本部门人员列表 |
| HR / 管理员 (Admin) | 系统管理员 | 全部权限：用户管理、部门管理、角色分配、查看全公司数据看板、二级审批（大额报销等） |

**权限模型说明**：采用 RBAC（Role-Based Access Control，基于角色的权限控制）。用户 → 角色 → 权限，是多对多关系（一个用户可以有多个角色，一个角色可以分配给多个用户），便于后续扩展（比如新增"财务"角色）。

## 3. 功能需求

### 3.1 用户与权限模块

| 功能 | 描述 | 涉及角色 |
|---|---|---|
| 注册/登录 | 员工使用工号或邮箱 + 密码登录，密码加密存储 | 全部 |
| JWT鉴权 | 登录后颁发Token，后续接口请求需携带Token校验身份 | 全部 |
| 用户管理 | 创建/编辑/禁用用户账号 | Admin |
| 角色分配 | 给用户分配一个或多个角色 | Admin |
| 修改密码 | 用户可自行修改密码 | 全部 |

**验收标准**：
- 密码字段禁止明文存储，需使用加密算法（如bcrypt）
- Token需设置过期时间，过期后需重新登录
- 未登录状态下，访问任何业务接口应返回401

### 3.2 组织架构模块

| 功能 | 描述 | 涉及角色 |
|---|---|---|
| 部门管理 | 创建/编辑/删除部门，支持部门层级（如"技术部"下设"后端组""前端组"） | Admin |
| 人员归属 | 每个用户归属一个部门，并指定直属上级 | Admin |
| 部门人员列表 | 查看某部门下的所有员工 | Admin, Manager（仅本部门） |

**验收标准**：
- 部门支持树形结构（父部门/子部门）
- 删除部门前需校验该部门下是否还有员工，有则禁止删除

### 3.3 审批流程模块（核心模块）

#### 3.3.1 请假审批

**流程**：
```
员工发起请假申请（类型、开始时间、结束时间、请假原因）
  → 系统创建审批记录，状态 = 待审批，审批人 = 申请人的直属上级
  → 审批人在"待办列表"中看到该申请
  → 审批人操作【通过】或【驳回】
      - 通过：状态变为"已通过"，通知申请人
      - 驳回：需填写驳回原因，状态变为"已驳回"，通知申请人
```

**请假类型**：事假、病假、年假、调休（可后续扩展）

**验收标准**：
- 开始时间不能晚于结束时间
- 同一员工同一时间段不能重复提交请假申请（时间区间不能重叠）
- 审批记录一旅创建不可删除，只能追加新状态（保证审计可追溯）

#### 3.3.2 报销审批

**流程**：
```
员工发起报销申请（金额、报销类型、附件凭证、说明）
  → 若金额 ≤ 阈值（如2000元）：仅需部门主管审批
  → 若金额 > 阈值：需部门主管审批通过后，再流转至HR/Admin二级审批
  → 任意一级驳回，流程终止，状态变为"已驳回"
  → 全部通过后，状态变为"已通过"
```

**验收标准**：
- 金额阈值应可配置（不写死在代码里）
- 二级审批场景下，需清晰展示当前审批处于第几级、审批人是谁

#### 3.3.3 审批记录查询

| 功能 | 描述 | 涉及角色 |
|---|---|---|
| 我的申请 | 查看自己提交的所有申请及状态 | 全部 |
| 待我审批 | 查看需要自己处理的审批任务 | Manager, Admin |
| 全部审批记录 | 查看全公司的审批历史记录，可按部门/状态/时间筛选 | Admin |

### 3.4 消息通知模块

| 触发场景 | 通知对象 | 通知方式 |
|---|---|---|
| 有新的待审批任务 | 审批人 | 站内消息（本期不做邮件/短信） |
| 申请被通过/驳回 | 申请人 | 站内消息 |

**验收标准**：
- 通知需标记已读/未读状态
- 用户登录后可在消息中心查看历史通知

### 3.5 数据看板模块（可选，视开发进度决定是否做）

| 功能 | 描述 |
|---|---|
| 部门请假统计 | 按部门统计本月请假人次、请假天数 |
| 审批时效统计 | 统计审批平均处理时长 |

## 4. 非功能性需求

| 类别 | 要求 |
|---|---|
| 安全性 | 密码加密存储；接口需JWT鉴权；敏感操作（如删除用户）需记录操作日志 |
| 数据一致性 | 审批记录不可篡改，只能追加状态变更，保证可追溯 |
| 性能 | 常规查询接口响应时间应在500ms以内（本期数据量小，暂不做重点压测） |
| 可维护性 | 代码需分层（路由层/业务逻辑层/数据层），禁止在路由函数里直接写SQL或业务逻辑 |
| 部署 | 使用Docker容器化部署，环境变量与代码分离（.env管理配置，不硬编码密钥） |

## 5. 数据流转示意（以请假审批为例）

```
1. 员工A提交请假申请
   POST /api/v1/approvals/leave
   { type: "annual", start_date: "2026-08-01", end_date: "2026-08-03", reason: "家庭旅行" }

2. 系统处理
   - 校验时间合法性
   - 查询员工A的直属上级（假设是主管B）
   - 创建审批记录：status = pending, approver = B

3. 主管B登录系统，进入"待我审批"列表，看到该记录

4. 主管B操作
   POST /api/v1/approvals/{id}/action
   { action: "approve" }  或  { action: "reject", reason: "时间冲突，请调整" }

5. 系统更新
   - 状态更新为 approved / rejected
   - 创建通知记录，推送给员工A
```

## 6. 待确认问题（Open Questions）

在开发前需要进一步明确的问题，避免开发中反复返工：

1. 请假类型的额度是否需要限制？（如年假每年固定天数，超出是否允许申请）
2. 员工离职/部门调整后，历史审批记录如何处理？
3. 是否需要支持"审批人不在时，自动转交给其他人代理审批"？
4. 报销附件（发票图片）存储方案：本地存储 or 对象存储（阿里云OSS等）？

> 这些问题本期先给出简化方案（比如附件先用本地存储，代理审批本期不做），后续迭代再完善。写在这里是为了明确"已知的技术债"，而不是假装没有这个问题。

## 7. 版本规划（MVP优先级）

| 优先级 | 模块 | 说明 |
|---|---|---|
| P0（必须） | 用户认证 + RBAC权限 | 系统基础，其他模块都依赖此模块 |
| P0（必须） | 组织架构管理 | 请假审批需要"直属上级"关系，依赖此模块 |
| P0（必须） | 请假审批流程 | 核心业务场景 |
| P1（重要） | 消息通知 | 提升体验，非阻塞性功能 |
| P1（重要） | 报销审批（含二级审批） | 核心业务场景，复杂度高于请假 |
| P2（可选） | 数据看板 | 时间允许再做，作为加分项 |

建议按P0 → P1 → P2的顺序开发，每完成一个模块走一次"设计→开发→测试→提交PR"的完整流程。
